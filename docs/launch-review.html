Source Kit Open Launch Review

The cryptography holds up under a hostile read, and the validation lab reproduces its headline numbers exactly. The packaging around it is what will cost you — starting with a repository whose own CI goes red on the first push.

16 Aug 2026 sourcekitopen 0.18.3 · ~43.7k LOC sourcekit 0.18.3 · ~61.6k LOC 39 suites executed

The short version. This is materially better engineering than most security tooling that gets published, and it is better than its own README makes it look. I ran the validation lab against the real shipping code: 1,192 checks passed across 39 suites, and the four suites that failed did so because an optional external tool was missing, not because anything was wrong — with c2patool installed, all four go green and land on the exact numbers the README claims (19/19, 18/18, 18/18). The X.509 verifier, the App Attest binding, and the attestation relay are each stronger than the norm.

What will hurt you is entirely in the wrapper. Two of four CI jobs fail on a clean checkout, so the repo lands with a red badge. The quickstart tells skeptics to run three commands and expect specific numbers; two of those commands fail for anyone who skipped the parenthetical dependency, and one prints 146 where the README promised 25. And 219 of 281 source files open with a comment telling the reader the file is "still being audited. Use with caution." On a tool whose entire pitch is show your work, that line is the first thing a reviewer at Apple or the AP reads, and it undercuts the 1,192 passing checks sitting directly behind it.

None of the blockers are deep. They are roughly a day of work, and they are the difference between "impressive research release" and "the project's own tests don't pass."

02 — BlockersFix these before you push

Ordered by how much damage each does in the first ten minutes a stranger spends with the repository.

B-1Your own CI fails on a clean checkout — the repo lands with a red badgecritical

The supply-chain job runs two things that both fail today. node scripts/check-dependency-budget.mjs exits 1: @noble/curves resolves to two versions (1.8.0, 2.2.0) and @noble/hashes to three (1.7.0, 1.7.1, 2.2.0) in the desk lockfile, and neither split is declared in KNOWN_VERSION_SPLITS. Separately, npm audit --audit-level=high in desk/ reports a high-severity nanoid advisory (GHSA-2v37-7h3g-55p8).

This is the cruelest possible failure mode, because the script is your own idea and a good one. A visitor sees a red X on a repository that argues for rigor.

FixRun npm audit fix in desk/, then either declare the two noble splits in KNOWN_VERSION_SPLITS with the vetting reason, or dedupe them. Re-run both commands locally until they exit 0 before the first push.
B-2Two of the three "Reproduce our results" commands fail without c2patoolcritical

The README lists c2patool parenthetically — "and (for the independent checks) c2patool" — then prints three commands and the words "Expected: 19 passed, 0 failed, 18 passed, 0 failed…". A reader who treats a parenthetical as optional runs those exact commands and gets five and two hard FAIL lines reading spawnSync c2patool ENOENT.

The suites treat a missing optional tool as a test failure rather than a skip. The crypto is fine; the harness is lying about it.

FixMake the c2patool checks skip loudly when the binary is absent — print SKIP (c2patool not on PATH — install to run the independent-verifier checks) and exclude them from the pass/fail tally. Then the honest headline is "14 passed, 5 skipped" and nothing is red. Also promote c2patool out of the parenthetical into a real requirements list with an install line.
B-3219 of 281 source files tell the reader not to trust themcritical

Every one of these files opens with:

// This file was generated with AI assistance and is still being audited. Use with caution.

It sits on top of x509.ts, cipher.ts, server.mjs, passcode.ts — the exact files whose correctness is the product. I read several of them closely and the banner is materially inaccurate: x509.ts enforces basicConstraints, keyCertSign, pathLen, fail-closed critical extensions, RSA exponent and modulus floors, and strict PKCS#1 v1.5 comparison. That is a more careful verifier than most shipped ones. "Still being audited" is not what that file is.

Disclosure of AI assistance is right and I would keep it. The problem is the second clause. As written it reads as a liability disclaimer stapled to a security tool, and it hands any critic a one-line quote that discredits 1,192 passing checks.

FixReplace the per-file banner with one honest, specific paragraph in the README and a short docs/PROVENANCE.md: how the code was written, what was reviewed by hand, what the suites cover, what remains unreviewed. If you keep a per-file marker, make it a neutral fact — // Written with AI assistance. Verified by tests/<suite>.mts — not a warning against use. Say what is true rather than pre-emptively discrediting yourself.

B-4npm test is broken; package.json is marked privatehigh

The root package.json points test:core, test:real and test:verify at scripts/test-core.mts, scripts/test-real.mts and scripts/test-verification.mts. None of those three files exists in the open tree — they were left behind in the private app repo, where scripts/ still holds them. So npm test, the first thing many developers type, fails instantly. typecheck likewise points at a tsconfig.json that is not in this tree.

The manifest also still carries "private": true and the full Expo app dependency set (expo-router, expo-image-picker, react-native-screens…) though the app shell is deliberately excluded — so the dependency list overstates the surface a reader is being asked to audit.

FixRepoint test at the staging flow (node tests/stage.mjs && …), drop "private": true, and prune dependencies to what the published tree actually imports.
B-5No NOTICE file — the one mechanism that would enforce your credithigh

You said credit matters most. Apache-2.0 §4(d) obliges every downstream redistributor to reproduce the contents of a NOTICE file if the work has one. You don't have one, so today a fork can legally strip your name to a line in a LICENSE header almost nobody reads. This is the single highest-leverage file you are missing, and it takes five minutes.

Related: LICENSE currently reads "Copyright 2026 Source Kit contributors". For a solo release where credit is the point, that should be your actual name.

FixAdd a NOTICE naming you as author with the project URL, put your name in the copyright line, and add a CITATION.cff so press and academics have a canonical citation. Full strategy in §4.
B-6README quickstart promises 25 checks; the suite prints 146high

The quickstart block says test-verification.mts # 25 checks and "Expected: … 25 passed, 0 failed". It actually prints 146 passed — a figure the README itself quotes correctly forty lines later. The quickstart is simply stale.

Under-promising is not harmless here. A skeptic who sees any number disagree with the documentation starts checking whether the other numbers are real, and that is exactly the reflex this project exists to earn.

FixRegenerate the quickstart figures from a real run. Better: have CI write the numbers into the README so they cannot drift again.

03 — AuditSource Kit Open, file by file

What I read closely: the X.509 verifier, the attestation relay, vault crypto and passcode handling, the Desk web app's attack surface, the CI pipeline, and the dependency posture.

What is genuinely strong

The X.509 chain verifier is better than most production onescommendable

src/lib/x509.ts does the things hand-rolled verifiers almost always skip: basicConstraints CA:TRUE on every non-leaf, keyCertSign discipline in both directions, pathLenConstraint honored, fail-closed on unrecognized critical extensions, RSA exponent ≥3 and odd, modulus ≥2048 bits, strict full-block PKCS#1 v1.5 comparison (which closes Bleichenbacher-style forgery), byte-exact issuer/subject chaining, ambiguous certificate sets refused rather than guessed, and validity evaluated at the verified signing time rather than the local clock. The DER reader's multiply-accumulate length parse, with its comment explaining the 32-bit signed wrap that used to hang the walker, is exactly the kind of thing that earns trust.

The App Attest binding is correct and completely checkedcommendable

server/server.mjs verifies the chain to a source-embedded pinned Apple root, checks the aaguid, confirms credId equals SHA-256 of the credential key, confirms the leaf's public key is the attested credential key (blocking mix-and-match of two genuine attestations), and re-derives the nonce with a real DER walk to the Apple OID. The emulated-key-attestation construction is the right answer to Apple's restriction and it is bound end to end. Rate limiting keyed on the attested keyId after verification — because an attacker can rotate IPs but cannot mint keyIds — is a genuinely sharp piece of design.

Discipline signals a reviewer will noticecommendable

Zero TODO/FIXME/HACK markers in your own code (the one hit is in vendored Adobe source). Zero console.log in shipped paths. No eval, no innerHTML, no dangerouslySetInnerHTML anywhere in the Desk. equalBytes is constant-time and used for hash comparison. CI pins actions to full commit SHAs and verifies the c2patool tarball's SHA-256 before extraction. PBKDF2 at 600k iterations with per-record work factors and transparent migration. The bannedWords.ts mechanism — enforcing in tests that no verdict-position copy says "verified" or "authentic" — is the most quietly impressive thing in the repository and should be in your launch pitch.

Real issues

O-1Desk ships no Content-Security-Policy, weakening its central claimmedium

The Desk's title literally reads "media custody checking, entirely in this browser", and I confirmed there are no fetch calls in its source. But desk/index.html carries no CSP. The claim is asserted in prose when it could be enforced by the browser — which is precisely this project's philosophy applied to itself.

FixAdd a restrictive CSP meta tag (default-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none', relaxing connect-src only to declared connector hosts). Then "nothing leaves this browser" becomes a mechanical guarantee a reviewer can verify in one glance at the HTML.
O-2The Desk verifies with different crypto library versions than the app signs withmedium

Root package.json pins @noble/curves 1.9.7 and @noble/hashes 1.8.0. desk/package.json pins 1.8.0 and 1.7.1, and the lockfile drags in 2.2.0 as well. The README says the Desk imports "this same src/ tree (never a fork)" — true of your code, but not of the primitives underneath it. A verifier and a signer disagreeing on crypto library versions is a legitimate question an auditor will ask, and it is the same drift that fails B-1.

FixAlign the noble versions across root, desk and server, and state the shared pin in the README where the "never a fork" claim is made.
O-3Four names for one product, in the files a newcomer opens firstmedium

The README's opening note handles this thoughtfully and I would not re-litigate the decision to freeze shipped identifiers. But the drift goes past identifiers into presentation: desk/package.json is "name": "exhibit-c", "version": "0.15.0" against a repo at 0.18.3; the CLI greets you with "exhibit-desk is now exhibit-c — this shim forwards…"; "Exhibit A" appears in 27 files. A reader meets Source Kit, Source Kit Desk, exhibit-c, exhibit-desk and Exhibit A within about four minutes.

FixKeep com.verify.camera and the URL scheme frozen — that reasoning is sound. But sync desk/package.json's version to the repo's, and either finish the CLI rename or drop the shim notice. One product name in every user-facing string.
O-4Chain anchoring never checks the pinned root's own validity windowlow

In verifyChain, presented certificates are all checked against atMs, but the loop that tests candidate pinned roots parses each root and verifies the signature without evaluating the root's notBefore/notAfter. Defensible — a pinned root is trusted by pinning, and the Apple root runs to 2045 — but it is an unstated asymmetry in a file whose docblock enumerates precisely what "verified" means.

FixEither check it, or add one line to that docblock saying pinned roots are exempt from the validity window and why.
O-5Critical extKeyUsage is accepted but not enforcedlow

RECOGNIZED_CRITICAL_EXTENSIONS includes extKeyUsage, so a certificate marking EKU critical passes chain verification without the constraint being honored. To your credit the code comments state this asymmetry explicitly, and the TSA path does enforce id-kp-timeStamping separately (test-tsa-eku, 9/9). So the practical exposure is small — but the general chain verifier accepts a must-understand extension it does not understand, which is the one rule the same file otherwise enforces rigorously.

FixLow priority. Consider enforcing EKU when present-and-critical, or file it as a public "good first issue" — it is a well-scoped invitation for an outside contributor.
O-6Stale security constant in a comment: 60k vs 600klow

src/lib/pinLockout.ts line 5 states "PBKDF2 (60k iterations) makes brute force expensive". The actual value in passcode.ts is 600,000 — ten times better than advertised. Also, pinLockout writes to SecureStore without the WHEN_UNLOCKED_THIS_DEVICE_ONLY accessibility option that passcode.ts uses for the credential it protects, so the lockout record and the passcode record have different backup/sync exposure.

FixCorrect the comment; pass the same OPTIONS to the lockout store. In a codebase this comment-dense, a wrong security constant is worse than no comment.
O-7Open-source hygiene files are entirely absentlow

Missing: NOTICE, CONTRIBUTING.md, CODE_OF_CONDUCT.md, CITATION.cff, CHANGELOG.md, issue and PR templates, dependabot.yml, .editorconfig. SECURITY.md is present and genuinely excellent — specific, honest about being part-time, explicit that there is no bounty. It sets the bar the others should meet.

FixSee the runbook in §5. Given you don't intend to maintain this long-term, CONTRIBUTING.md and a governance note matter more than usual, not less.

On the comments

You asked specifically about superfluous comments. The codebase is 25.9% comment lines — roughly 10,600 of 40,800 non-blank lines — peaking at 68% in desk/stereo/types.ts and 60% in contracts-ext.ts. That is far above normal, and my honest read is that most of it earns its place. These are not restatements of the code; they are threat rationale, rejected alternatives, and citations to the spec clause being honored. For a project whose thesis is "show your work," that is the work, and I would not strip it.

Two caveats. First, a large share of comments narrate bugs you previously shipped: "a one-request remote DoS on this public endpoint", "the overrun guard passed against a negative length", "silently PASSED for unparseable dates". As engineering culture this is admirable. As published text it is quotable out of context, and a hostile write-up would have no trouble assembling those fragments into a paragraph about your app's history of vulnerabilities. I would keep them — the honesty is the differentiator, and hiding them would be worse — but move the most dramatic ones into docs/SECURITY.md's audit history where the framing is yours, and leave the code comment as the terse invariant.

Second, comment drift is now a real risk at this density: O-6 is one wrong security constant already, and nothing checks for more. Density this high needs the same regression discipline as the rest of the project.

05 — StrategyCredit, licensing, and stopping the wrong kind of monetization

Your stated goals: maximum adoption by news organizations, Google and Apple; guaranteed credit; and nobody monetizing it in a way that discourages others from using it. Those pull in different directions, and the resolution is not the license.

Recommendation

Keep Apache-2.0. Add a NOTICE file, assert the trademark, and add a CITATION.cff. The license is already the right one; what's missing are the three instruments that actually deliver credit and restrain free-riding.

Why not copyleft, given what you want

The instinct to reach for AGPL to block commercial capture is understandable, and it would defeat your primary goal. Google's open source policy prohibits AGPL software outright, and Apple has avoided strong copyleft in its platforms for many years. Choosing AGPL would mean the two organizations you most want to hand this to are structurally unable to pick it up. Apache-2.0's explicit patent grant (§3) is also a large part of why corporate legal teams can adopt it quickly — and for a provenance and crypto tool, patent peace is not a footnote.

So: the license that maximizes your stated top priority is the one you already have. Achieve the other two goals with the instruments built for them.

The three things to add

  • NOTICE — this is your credit enforcement. Apache-2.0 §4(d) requires every downstream redistributor to reproduce your NOTICE contents in their distribution. It is the only part of the license that compels attribution to travel. Without it, a fork can bury you. With it, your name and project URL ride along legally. This is the single highest-value file you are missing.
  • Trademark — this is your anti-monetization lever. Apache-2.0 §6 explicitly grants no trademark rights. So while anyone may fork the code, nobody may ship it as "Source Kit". That is the real protection against a company monetizing your work in a way that confuses or crowds out users: they must build their own brand, disclose the fork, and compete on merit. Add a TRADEMARK.md stating that the name and any logo are unlicensed, that forks must rename, and that you welcome accurate "built on Source Kit Open" attribution.
  • CITATION.cff — this is your research credit. GitHub renders it as a "Cite this repository" button and it gives journalists and academics a canonical form. For work you want cited in reporting and papers rather than sold, this does more than the license.

Also change the LICENSE copyright line from "Source Kit contributors" to your own name. "Contributors" is for projects with contributors; this is a solo release and you want it attributable.

The honest limit

Apache-2.0 permits a company to fork this, close their changes, and sell it. Nothing short of copyleft prevents that, and copyleft costs you the adoption you ranked first. What blunts it in practice: they cannot use your name, they inherit a codebase whose App Attest binding is tied to your Apple team identifier and bundle ID, and — the strongest deterrent — you will have published the reference implementation with a public validation lab. A closed fork that cannot show its work competes badly against one that can. Your test suite is a better moat here than any license clause.

06 — RunbookFrom zip to launched repository

An ordered sequence — each step assumes the previous one is done. Steps 1–3 are the day of work that turns this from risky to strong; everything after is launch mechanics.

01

Get to green before anyone sees it

Nothing else matters until the badge is green. Work locally, no repo yet.

  • cd desk && npm audit fix — clear the nanoid advisory (B-1)
  • Declare or dedupe the @noble/* version splits until node scripts/check-dependency-budget.mjs exits 0 (B-1)
  • Convert the c2patool checks from hard-fail to loud skip (B-2)
  • Repoint the test and typecheck scripts; remove "private": true (B-4)
  • Align noble versions across root, desk and server (O-2)

Verify: with c2patool absent, no suite prints FAIL. With it present, all 39 are green.

02

Fix the trust-destroying text

  • Strip the "still being audited. Use with caution" clause from all 219 files; write one honest docs/PROVENANCE.md about how the code was produced and verified (B-3)
  • Regenerate the quickstart numbers from a real run; promote c2patool to a real requirement (B-6)
  • Add the stereo caveat, or validate the fix on device (A-1)
  • Correct the 60k → 600k comment and the SecureStore options (O-6)

Do this as one commit with a clear message. It is the commit that makes the repository defensible.

03

Add the credit and governance instruments

  • NOTICE, your name in LICENSE, TRADEMARK.md, CITATION.cff (§5)
  • CONTRIBUTING.md — and be explicit that this is a reference release you do not intend to maintain long-term, that you welcome forks, and what you will and won't review. Setting that expectation up front is a kindness, and it prevents the resentment that kills goodwill around abandoned projects
  • CODE_OF_CONDUCT.md (Contributor Covenant), .editorconfig, .github/dependabot.yml, issue templates
  • A CSP meta tag in desk/index.html (O-1) — small, and it hardens your headline claim
04

Create the repository

Add .triage-*.md to the app repo's .gitignore first (A-2). Then, in the open tree:

git init
git add -A
git status          # read every path before the first commit
git commit -m "Source Kit open provenance core (0.18.3)"
gh repo create source-kit-open --public --source . --push

Read the git status output line by line. A first commit is the one moment where an accidental file is cheap to remove and expensive to forget.

Then in repo settings: enable Issues and Discussions, enable private vulnerability reporting (your SECURITY.md already directs people there), turn on Dependabot alerts, and add topics — c2pa, content-credentials, provenance, digital-forensics, ios, secure-enclave, journalism.

05

Confirm CI green, then tag

Watch the first Actions run to completion. All four jobs green, or go back to step 1 — do not publicize a red repository. Then tag v0.18.3 and cut a GitHub Release whose notes lead with the reproducible numbers, not the feature list.

Add the CI badge to the README only once it is green. A badge is a promise.

06

Write the deep dive as the front door

You want this read, not just available. The README is a reference document; the deep dive is the thing people share. Lead with the strongest true claim you have: every cryptographic claim in this document can be reproduced offline in about five minutes, and here is the command.

Structure that earns the audience you want:

  • The problem, in one newsroom-legible paragraph — custody, not reality
  • The architecture, with the two-axis integrity/credibility split as the centerpiece — it is your most original contribution and it is what a standards person will care about
  • The honesty machinery: bannedWords.ts, "what we will not build and why", the seven rejected analyses. Lead with this more than you think you should. Anyone can claim crypto; almost nobody enforces vocabulary discipline in CI
  • The reproduction section, with real terminal output pasted in
  • The limits: what is unchecked (TSA root anchoring, revocation), what is broken (stereo on iPhone 17), what you will not maintain

Publish it on your own domain and link it from the README, so the canonical version is somewhere you control.

07

Place it with the people you actually want

Targeted outreach beats broadcast for work at this level of specificity. In rough order of expected value:

  • C2PA / CAI community. The most likely place for genuine technical engagement. Your differential oracle — hand-rolled engine cross-checked against the upstream C2PA engine on every CI run — is a real contribution to conformance testing, and the CAI Discord and c2pa-rs discussions are where that lands
  • Newsroom technologists. Reuters, AP and AFP have provenance initiatives; BBC R&D and the NYT R&D group publish in this space. Send the Desk, not the app — a local verifier that runs offline in a browser is immediately useful to a picture desk
  • Freedom of the Press Foundation and Witness.org. Witness in particular has worked on media provenance for human rights documentation for years and thinks carefully about exactly your threat model
  • Apple and Google. Realistically these are inbound, not outbound — they come after the above give you credibility. Your Secure Enclave emulated-key-attestation construction is the piece with the clearest platform relevance
  • Show HN, titled for the reproducible claim rather than the app. That audience rewards "run this and check me" and punishes marketing

In every message, lead with the lab. "You can falsify my claims in five minutes, here's how" is a far stronger opening than any feature description, and it is the one thing this project can say that almost nothing else in the space can.

08

Plan for not maintaining it

You have said you won't maintain this long-term, which makes the handoff part of the deliverable rather than an afterthought. Concretely: state the maintenance posture in the README's first screen, not buried; keep CI pinned and reproducible so the lab still runs years from now; file the "good first issues" your PUBLISHING.md already drafts (they are well chosen — the Android port and the standalone verifier CLI are the two most likely to attract a real contributor); and add a short succession note saying you will consider transferring the repository to a suitable steward organization. For a reference implementation, an honest "this is finished, here is how to fork it" is a perfectly respectable end state — and far better than a repo that looks abandoned by accident.

07 — ClosingWhat this is worth

I went looking for reasons to distrust this codebase, because that is what a hostile reader will do. The specific things I checked hardest — whether the test numbers were real, whether the X.509 verifier cut corners, whether the App Attest binding actually binds, whether secrets had leaked, whether the Desk phones home — all came back clean. The 146-check verification suite runs the real shipping code against openssl-generated forgeries, and it passes. That is not nothing; most projects making claims at this volume cannot survive that check.

The risk to your reputation is not that someone finds a flaw in your cryptography. It is that someone clones the repository, sees a red CI badge, runs the three commands in the quickstart, watches two of them fail, opens x509.ts and reads "still being audited. Use with caution" — and closes the tab before reaching any of the work that would have impressed them. Every one of those is a packaging defect, and every one is fixable in a day.

Fix the wrapper. The contents are good.
